## Remaining findings, ordered by practical impact

### 1. Optional romanization is still a fatal dependency (high, code-confirmed)
LyricUtilities.ts: GetRomaji memoizes a rejected initialization promise, and
Promise.all(romanizationPromises) rejects the entire lyric transformation. Any
future romanizer failure can therefore hide valid native-script lyrics for the
rest of the session. The damaged data is repaired, but this architectural behavior
remains. Recommend degrading to native text with a warning, with controlled retry
rather than one retry per segment. Do not cache incomplete romanization as a fully
successful transformation.

### 2. LRCLIB matching is narrower than it could be (medium, code-confirmed)
AdditionalProviders.ts FetchLrclib makes one /api/get request using full title,
comma-joined artists, album and duration. No primary-artist/album-relaxed search,
romanized aliases or explicit edition selection. A legitimate exact miss can be
cached as false for two weeks, including when a successful response has no usable
parsed text. This can cause missed lyrics even though another metadata spelling
would match. Recommend a bounded, scored fallback search and shorter negative TTL.
This is a coverage limitation; it was not established as the cause of GHOST's old
preparation failure.

### 3. Monthly cache expiration is not a month-long TTL (medium, code-confirmed)
Cache.ts sets next month, then setDate(0): usually the last day of the current
month at midnight, not 30 days from insertion. Month-end overflow adds more edge
cases. Entries can expire much sooner than expected. Expired/version-mismatched
entries are ignored rather than deleted, so storage does not proactively clear.
Recommend explicit duration semantics and bounded cleanup on ordinary cache use.

### 4. One slow source delays every usable source (medium, code-confirmed)
LyricsProviders.ts awaits all provider jobs, then Player/mod.ts prepares candidates
serially. A good source can wait behind another source's timeout/queue, and all
candidates incur preparation even if never selected. Recommend progressive display
and lazy preparation of alternatives in a later behavior/performance pass.
No measured CPU/GPU claim is made here.

### 5. Any settings change clears Spicy's memory cache (medium, code-confirmed)
AdditionalProviders.ts subscribes spicyCache.clear to the general settings event.
Changing sidebar/fetch mode or an unrelated provider discards Spicy results and
can cause another paid/rate-limited request. Recommend invalidating on token or
Spicy-specific configuration changes only, while retaining the enabled checks.

### 6. Secondary backing vocals lack romanization (low, code-confirmed)
LyricUtilities.ts romanizes Background[0] only, while LyricsRenderer renders all
background tracks. Duet/backing lyrics after the first remain untranslated when
romanization is enabled. Recommend iterating all background tracks at preparation
 time; no animation-loop work is needed.

### 7. Sidebar compatibility/lifecycle still needs its own pass (unresolved)
Selectors are tied to older Spotify DOM. On the tested GHOST page, root, content
and insertion anchor ALL existed, so 'missing selector' alone is not a proven
cause. Sidebar was disabled in the user's saved settings, so this session did not
reproduce an enabled sidebar failure. CheckForSidebar also re-schedules via
requestAnimationFrame + timeout indefinitely if the root is absent while enabled.
Recommend a controlled enabled-sidebar repro before changing selectors; replace
indefinite discovery with host mount events or a bounded/narrow discovery strategy.

## Behavior differences, not proven bugs
- Spotify is not a provider in this fork; Lyrics Plus used it for GHOST. That is a
  genuine coverage gap, not evidence that our Spotify URI queries are malformed.
- Line-only results use fixed priority Musixmatch > Spicy > AMLL > LRCLIB, not line
  count. Thus GHOST selects Spicy's 41 over LRCLIB's 45; the selector still allows
  switching. Word-timed results use distinct timing count.
- Missing AMLL files returning 404 in Chromium's console are expected and retained
  by user preference. Do not reinstate the track index.
- Premium Spotify does not establish an unlimited lyric quota.
